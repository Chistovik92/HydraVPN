## План

### 0.7.9 — исправления устойчивости соединения (выпущено 08.10.2026)

Жалоба владельца: на Xray (и, возможно, на sing-box) через какое-то время — «после ~1,6 ГБ» — интернет
перестаёт грузиться до ручного переподключения; Xray не поднимается и зависает при уходе с Wi-Fi на LTE/5G
и обратно; sing-box периодически падает. Разбор на эмуляторе (локальный Shadowsocks-сервер, 4 бесконечных потока):

- Объём сам по себе ни при чём: через sing-box прошло 2,7 ГБ без сбоя; память, дескрипторы и потоки стабильны.
- Через Xray потоки замерли на ~690 МБ ровно в момент, когда sing-box сам переключил «интерфейс по умолчанию»
  с Wi-Fi на мобильную сеть, хотя Wi-Fi никуда не пропадал. Причина — монитор сети в `HydraPlatformInterface`:
  он сообщал ядру о той сети, о которой пришёл колбэк, а не о лучшей; любое событие мобильной сети (на телефоне
  с «мобильным интернетом всегда активным» это обычное дело) уводило ядро с Wi-Fi. А при уходе из Wi-Fi, если
  мобильная уже была поднята, `onAvailable` не приходил вовсе (`onLost` не обрабатывался) — ядро оставалось
  привязанным к исчезнувшему `wlan0`.

Что сделано: монитор на любое событие заново выбирает лучшую физическую сеть (`PhysicalNetwork.pick`: основная
сеть системы для приложения, иначе проверенная Wi-Fi → Ethernet → мобильная), повторы не шлёт, при отсутствии
сети сообщает «сети нет»; Xray получил TCP keep-alive (30 с / 15 с) и `domainStrategy: AsIs`. На ПК (владелец: «не только на
мобильных») — наблюдатель физических интерфейсов и автопереподключение при смене сети. По просьбе владельца в тот же релиз:
темы Android подтянуты к Material You (полная тональная схема M3), темы и иконки Android — на ПК и iOS. Что проверено и что
нет — CHANGELOG 0.7.9.

- **macOS:** подпись/бит исполнения клиентов в DMG, запуск клиента из-под привилегированного TUN без второго запроса

- **iOS:** gomobile-`xcframework` из закреплённых коммитов olcRTC и OpenFlux (в macOS-CI, как Libbox), запуск клиента внутри

  превышении отказ с понятной причиной; импорт `olcrtc://`, `openflux://`, `olcbox://`.
- Условия выпуска: OpenFlux `direct` — сквозной тест на всех ПК-ОС в CI; живые транспорты — проверка владельцем (нужны

### 0.8.0 — «Мои серверы»: SSH и свой AmneziaWG

Новая вкладка **«Мои серверы»** (Android и ПК; iOS — 0.8.3). Общий код — в `shared` (JVM-часть для Android и ПК).

1. **SSH-слой.** Клиент SSH (JSch-fork `com.github.mwiede:jsch`, BSD; ed25519/curve25519 — на Android через BouncyCastle):
   вход по паролю или ключу, **закрепление отпечатка хоста** при первом подключении (с показом пользователю), SFTP,
   потоковый вывод команд в журнал. Секреты (пароль/ключ) по умолчанию живут только в памяти сессии; «запомнить» —
   зашифрованно (Android Keystore; на ПК — файл, шифруемый ключом из системного хранилища). Из журнала секреты вырезаются.
2. **Движок установщика.** Сервер = набор шагов `Step(проверка → команда → проверка результата)`; предполётные проверки
   (ОС и разрядность, root/sudo, свободные порты, `systemd`, интернет с сервера, занятость портов); идемпотентность
   (повторный запуск не ломает), откат/удаление, показ команд до запуска («что будет выполнено»), стоп-кнопка.
3. **Свой сервер AmneziaWG.** Выбор поколения: **1.0** (Jc, Jmin, Jmax, S1, S2, H1–H4), **1.5** (+ I1–I5), **2.0** (+ S3, S4,
   H-диапазоны), **3.x** (+ HeaderProtectionKey, ContentPaddingAddition, таймеры, RandomTrailers, DisableCookies) — соответствует
   `AwgParams`. Серверная сторона: статический `amneziawg-go` (userspace, без модуля ядра/DKMS) под linux amd64/arm64/armv7,
   **собираем в нашем CI и подписываем SHA-256**, заливаем по SFTP; `systemd`-сервис, `ip_forward`, NAT (nftables/iptables),
   открытие порта (ufw/firewalld — только по согласию). Ключи X25519 (+ PresharedKey) создаёт приложение; параметры обфускации
   — случайные в допустимых пределах (соблюдая правила: Jmin < Jmax, S1 + 56 ≠ S2, H1–H4 различны и не пересекаются).
   Результат: профиль сервера появляется в списке **автоматически**, клиентов можно добавлять и удалять, показывать QR/`.conf`.
   Критерий готовности: на настоящем VPS (Debian/Ubuntu x64 и arm64) все четыре поколения подключаются клиентами Hydra, а
   `awg show` на сервере видит handshake.
4. Альтернатива (0.8.1): AmneziaWG-инбаунд внутри 3x-ui v3.9 (встроенный userspace-стек).

Требует: **живой VPS для проверки** (у владельца), CI-сборка серверного бинаря.

### 0.8.2 — Панели 2 и «подписка в один клик»

- **PasarGuard (v5.4.1):** `pasarguard.sh @ install [--database …]`; дашборд требует TLS; владелец создаётся одноразовым ключом
  `pasarguard cli generate-temp-key` (читаем по SSH и создаём учётную запись через API); вход — `/api/admin/token`.
- **Remnawave (3.4.4):** Docker Compose (панель + БД + Redis/Valkey) за обратным прокси, нужен домен; ставим только при домене и
  открытых 80/443; вход по Bearer-токену API; страницы подписки — отдельный `subscription-page`.
- **Nexora (v0.0.2):** `bash <(curl -fsSL …/install.sh)`; без вопросов, порт и пути выбирает установщик (случайно), мастер

## Фаза 13 — управление роутером (HydraVPN for Router)

Роутерная часть — отдельный репозиторий
[Chistovik92/HydraVPNforRouters](https://github.com/Chistovik92/HydraVPNforRouters) (Go, v1.0.4 на
30.09.2026): сервис `hydravpn-router` на OpenWRT (IPK, LuCI), KeeneticOS (Entware) и MikroTik
RouterOS 7 (контейнер); ядра sing-box, zapret/zapret2, ByeDPI; конфиг —
`/etc/hydravpn-router/config.yaml` (секции, подписки, urltest, списки, DNS/FakeIP).
Цель фазы — чтобы роутером можно было управлять из приложения Hydra, как VPN на самом устройстве.

**Что у роутера уже есть (сверено 30.09.2026, main, v1.2.0).** Управляющий API `/api/v1/*`
(`internal/mgmt`, [docs/API.md](https://github.com/Chistovik92/HydraVPNforRouters/blob/main/docs/API.md)):
`version`, `status`, `config`, `reload`, `restart`, `sections` (CRUD), `subscriptions` (добавить/удалить/
`refresh`), `servers`, `nodes` (+ `select`, `test`), `logs` (+ SSE `logs/stream`), `check/{name}`.
Доступ: `Authorization: Bearer <token>`, только частные сети (`api_allow`), 10 неверных токенов в минуту →
429, журнал аудита, TLS по `api_tls_cert/key`. Ссылка сопряжения:
`hydravpn-router://host:port?token=…&tls=1&fp=<sha256>` (`hydravpn-router pair --host …`).
Старый Clash-подобный `internal/api` удалён. Клиент `RouterClient` (`:shared`) написан под этот контракт.

Состояние работы и что продолжить — [HANDOFF_ROUTERS.md](HANDOFF_ROUTERS.md).

**Не закрыто (нужно в роутере):** `/api/v1/capabilities` для старых версий; права «смотреть/управлять»
(токен один, полный доступ); `?token=` принимается на любом пути (нужно только для SSE); автогенерация
самоподписанного сертификата (сейчас TLS — вручную); `/traffics` и соединения (Clash-эндпоинты не
проброшены); mDNS `_hydra-router._tcp`; откат конфига при ошибке `sing-box check` (есть только `.bak`).

**13a. Подключение к роутеру (клиенты).** Экран «Роутеры»: добавить по адресу + секрету или по
QR/ссылке `hydravpn-router://host:port?token=…&tls=1&fp=…` из LuCI/веб-UI роутера; поиск в локальной сети
(mDNS `_hydra-router._tcp` — нужна поддержка в роутере; до неё — ручной ввод и шлюз по умолчанию).
Секрет — в защищённом хранилище (Android Keystore / Keychain / файл 0600 на ПК). Общая логика
клиента API — в `:shared` (Android и ПК), для iOS — в `HydraKit`.

**13b. Мониторинг и узлы (только существующий API).** Статус и версия сервиса, скорость и
трафик (`/traffics`), активные соединения с разрывом, журнал (`/logs`), список групп и узлов с
задержкой и выбором узла (`/proxies`). Виджет/плитка «роутер: онлайн, узел, скорость».

**13c. Управляющий API в роутере (изменения в HydraVPNforRouters).** Расширение `/api/v1/…`: секции (вкл/выкл, action, provider, community_lists, fully_routed_ips), подписки
(добавить/удалить/обновить сейчас/интервал), списки и rule_set, DNS, «применить и перезапустить»
с откатом конфига при ошибке `sing-box check`, обновление компонентов. Версионирование API и
`/api/v1/capabilities`, чтобы клиент скрывал то, чего старый роутер не умеет.

**13d. Управление из клиентов.** Редактор секций и подписок роутера; **«Отправить на роутер»**
для сервера или подписки из Hydra (одна кнопка вместо ручного копирования ссылки в LuCI);
перенос правил маршрутизации Hydra (домены/IP/страны) в секцию роутера; «весь трафик этого
устройства через роутерный VPN» (fully_routed_ips по IP устройства).

**Безопасность (обязательно до 13c).** Сейчас API роутера — HTTP с bearer-секретом: в Wi-Fi
секрет можно перехватить, а управляющий API даст полный контроль над роутером. Нужно: секрет
обязателен при прослушивании не-localhost; только LAN-интерфейсы; TLS с самоподписанным
сертификатом и **закреплением отпечатка** при сопряжении (QR несёт отпечаток); ограничение
попыток; отдельные права «смотреть» / «управлять».

  ни транспорт, ни смена сети не могут изменить `VpnState.state`. Худший
  сценарий — «зомби-туннель»: PPP закрыт/ядро умерло/Wi-Fi сменился на
  LTE, в UI по-прежнему «Туннель зашифрован», трафик не идёт, Kill Switch
  не срабатывает (он живёт только внутри `doConnect()`), и пользователь
  не знает, защищён он или нет.

  **Найденное — критическое (тихая потеря связи):**
  1. **Смерть ядра не отслеживается.** Интерфейс `VpnCore`
     (`vpn/core/VpnCore.kt`) — это `start()`/`stop()` без канала «я умер»:
     у ядра нет способа сообщить наверх об аварии. Места, где сигнал уже
     есть и выбрасывается в лог: `SstpCore.kt:168` (`onDown` PPP —
     `onLog(...)` и всё), `L2tpCore.kt:48-50` (`onTunnelDown` от
     StopCCN/CDN — `onLog(...)` и `running = false`). У sing-box канала нет
     вовсе: `BoxService` может закрыться, `SingBoxCore.service` об этом не
     узнает.
  2. **Смена сети не обрабатывается.** `HydraVpnService` не регистрирует
     `NetworkCallback` и никогда не зовёт `setUnderlyingNetworks()` —
     система продолжает считать подложкой ту сеть, что была на момент
     `establish()`. Единственный монитор сети в проекте живёт внутри
     `HydraPlatformInterface.startDefaultInterfaceMonitor()`
     (`SingBoxCore.kt`) и обслуживает только sing-box; для SSTP/L2TP
     транспортный сокет при Wi-Fi→LTE просто умирает.
  3. **Переподключения нет ни в каком виде** — ни retry с бэкоффом при
     неудачной попытке, ни reconnect после разрыва. Любая ошибка =
     `ERROR` до ручного тапа пользователя.
  4. **PPP без таймеров.** `sendLcpConfigRequest()` (`PppSession.kt:89`)
     отправляется ровно один раз: потерянный ConfReq/ConfAck — это
     ожидание до общего таймаута в `SstpCore`, без единой повторной
     попытки (RFC 1661 требует Restart-таймер). Свой Echo-Request мы не
     шлём — только отвечаем на чужой (`PppSession.kt:136`), так что
     молча умерший peer не детектируется.

  **Найденное — утечки потоков и ресурсов:**
  5. `TunBridge.stop()` (`TunBridge.kt:94`) ставит только `running = false`:
     поток `tun-ppp-read` (`:51`) остаётся навсегда висеть в блокирующем
     `input.read()`, `FileInputStream`/`FileOutputStream` поверх tun
     никогда не закрываются, поток `tun-bridge-stats` (`:79`) досыпает
     свой `Thread.sleep(1000)` без interrupt. При переподключении/смене
     сервера потоки накапливаются, а старый читатель продолжает толкать
     пакеты в уже закрытую сессию.
  6. `downBytes`/`upBytes` (`TunBridge.kt:31`) — обычные `Long`: пишутся из
     потока-читателя tun и из колбэка транспорта, читаются из потока
     статистики. Гонка, рваные значения счётчиков.
  7. `SubscriptionFetcher` (`:13`) создаёт **свой** `OkHttpClient` (со
     своим пулом потоков и коннекций) на каждый экземпляр
     `ServerRepository` — а репозиторий конструируется заново в
     `MainViewModel`, `HydraVpnService.doConnect()`, QS-плитке и
     `BootReceiver`.
  8. `AppDatabase.get()` (`:21`) — double-checked locking **без второй
     проверки** под `synchronized`: при гонке двух потоков собираются два
     инстанса Room на один файл.

  **Найденное — крэши и ANR-риски:**
  9. `startForegroundService()` не обёрнут ни в `BootReceiver.kt:37`, ни в
     `HydraQsTileService.kt:76`; `startForeground()` в
     `HydraVpnService.onStartCommand()` — тоже голый. На Android 12+ это
     `ForegroundServiceStartNotAllowedException` → краш процесса в фоне,
     который пользователь увидит как «после перезагрузки VPN не поднялся».
  10. Нет `Thread.setDefaultUncaughtExceptionHandler`: исключение в любом
      из ручных `thread {}` (`sstp-reader`, `l2tp-reader`, `tun-ppp-read`)
      уносит процесс, не оставив ни строчки в `LogStore` — разбирать
      потом нечего.
  11. `VpnState.log()` (`VpnState.kt:43`) — неатомарный
      read-modify-write `_logs.value = (_logs.value + …).takeLast(500)`,
      причём зовётся с JNI-потоков sing-box на горячем пути: часть строк
      теряется, и каждая строка аллоцирует новый список на 500 элементов.
      `LogStore.append()` (`:29`) складывает задачи в **неограниченную**
      очередь однопоточного executor'а — всплеск логов ядра растит кучу.
  12. `measureAllPings()` (`MainViewModel.kt:336`) — по корутине на сервер
      без ограничения параллелизма: на подписке в сотни серверов это
      сотни одновременных TCP-connect и столько же записей в Room.

  **Найденное — целостность данных:**
  13. `refreshSubscription()` (`ServerRepository.kt:34`) делает
      `deleteBySubscription()` + `upsertAll()` **не в транзакции**: падение
      между ними (или успешный ответ с пустым телом) стирает серверы
      подписки. Плюс id пересоздаются, из-за чего `lastServerId` повисает
      на несуществующем сервере.
  14. Room `version = 1` + `fallbackToDestructiveMigration()` — риск уже
      записан в 6d выше, здесь он просто самый дешёвый к починке из
      оставшихся.

  **План починки (порядок = порядок ценности, каждая подфаза
  самодостаточна и проверяема отдельно):**

  - ✅ **7a. Наблюдаемость туннеля** (0.6.14, **на устройстве не проверено,
    native-флейвор даже не компилировался** — см. CHANGELOG): в `VpnCore`
    появился `setDeathListener` (дефолтная реализация — no-op, поэтому ядра
    без такого сигнала правок не потребовали), и в него заведено то, что
    раньше уходило только в лог: обрыв TLS-канала / CALL_ABORT / закрытие
    PPP в `SstpCore`, StopCCN-CDN / закрытие PPP в `L2tpCore`, смерть
    процесса `:xray` (`onServiceDisconnected`) в `XrayCore`.
    `HydraVpnService` принимает сигнал через `Attempt` — маркер попытки,
    отличающий смерть у живого туннеля от смерти внутри `start()` (её
    по-прежнему разбирает catch в `doConnect`) и от эха уже проигравшей
    попытки при переключении сервера. Kill Switch вынесен в
    `enterKillSwitch()` и теперь защищает оба случая, а не только неудачное
    подключение; уведомление различает «Ошибка подключения» и «Туннель
    разорван».
    **Открытый хвост 7a — sing-box.** Признака «ядро умерло» в libbox не
    нашлось, и основной движок фазой пока НЕ покрыт. Отклонены два
    кандидата: `CommandClientHandler.disconnected()` — это обрыв нашего же
    локального сокета к `CommandServer`, возможный и при живом ядре, а
    ложное срабатывание погасило бы рабочее соединение (теперь просто
    пишется в лог); `CommandServerHandler.postServiceClose()` — по
    устройству libbox это запрос клиента на остановку, а не уведомление о
    смерти. Нужный признак надо сверять с настоящим `libbox.aar`
    декомпиляцией — тем же способом, которым в 0.6.6 сверялся API Xray.
    Пока его нет, 7b для sing-box бессмысленна: переподключать нечего,
    если разрыв не виден.
    Критерий готовности (НЕ выполнен, нужен телефон): убитый на сервере
    туннель за ≤5 с меняет UI и уведомление, а не остаётся «зашифрованным».
  - **7b. Переподключение.** Поверх 7a: `reconnect()` с экспоненциальным
    бэкоффом (1/2/4/8/16 с, потолок ~1 мин, счётчик сбрасывается после
    минуты живого соединения), состояние `RECONNECTING` в
    `ConnectionState` (UI-строка + отдельный вид reactor-кнопки), лимит
    попыток и честный переход в `ERROR` после него. Kill Switch держит
    tun «чёрной дырой» **всё время** переподключения — это главный
    смысл фазы. Отдельный тумблер «Переподключаться автоматически» в
    Настройках → Безопасность, рядом с Kill Switch.
  - **7c. Сеть под туннелем.** `NetworkCallback` уже в самом
    `HydraVpnService` (с `NET_CAPABILITY_NOT_VPN`, как в
    `HydraPlatformInterface` — тот же урок про собственный tun в роли
    «дефолтной сети»), `setUnderlyingNetworks(arrayOf(network))` при
    каждой смене, и триггер reconnect из 7b при смене транспорта
    (Wi-Fi ⇄ LTE). Для sing-box существующий монитор в
    `HydraPlatformInterface` остаётся как есть — фаза не должна его
    дублировать, только дополнить уровнем сервиса.
  - **7d. Жизненный цикл потоков и ресурсов.** `TunBridge.stop()` —
    закрывать потоки ввода-вывода (закрытие fd разблокирует
    `input.read()`), `join(timeout)` на оба потока, `interrupt()` для
    статистики; счётчики → `AtomicLong`. `PppSession` — Restart-таймер
    для ConfReq (3 попытки по 3 с, как в RFC 1661) и собственный
    LCP Echo-Request раз в 30 с с детектом трёх пропущенных ответов
    (это же и есть недостающий keepalive для 7a). Один общий
    `OkHttpClient` на процесс; `AppDatabase.get()` — вторая проверка под
    `synchronized`.
  - ✅ **7e. Дешёвая страховка** (0.6.15, кроме ограничителя лога — только
    компиляция stub в CI, живьём не проверено): `runCatching` вокруг всех
    трёх стартов foreground-сервиса (`BootReceiver`, `HydraQsTileService`,
    `HydraVpnService.onStartCommand` — последний при отказе честно гасит
    сервис вместо падения); глобальный `UncaughtExceptionHandler` пишет
    стек в `LogStore` и ждёт сброса на диск (`flushBlocking`) до передачи
    системному обработчику; `VpnState.log()` переведён на атомарный
    `update {}` и получил `LogThrottle` (40 строк/с, WARN/ERROR не режутся,
    проглоченные считаются — вынесен отдельным классом с внешними часами
    ради JVM-тестов, как `LogFiles` в 6d); очередь `LogStore` ограничена
    2048 задачами с `DiscardPolicy`; `measureAllPings()` — `Semaphore(8)`;
    `ServerDao.replaceSubscriptionServers()` под `@Transaction` + отказ
    применять пустой ответ подписки (и причина отказа теперь видна в логе,
    а не «импортировано 0 серверов»); вторая проверка под `synchronized` в
    `AppDatabase.get()`.
    **Порядок нарушен сознательно:** 7e сделана раньше 7b-7d, потому что
    7b (переподключение) для основного движка упирается в открытый хвост
    7a — без признака смерти sing-box переподключать нечего, — а вся 7e
    лежит в `app/src/main` и потому проверяется компиляцией CI, тогда как
    правки в native-флейворе здесь не компилирует никто.

  **Что осознанно НЕ входит в фазу 7**: миграции Room (пункт 14 — вместе
  с первым же изменением схемы, как и записано в 6d); переживание
  `onRevoke()` (система сама снимает tun, защищаться нечем); watchdog по
  отсутствию трафика (счётчики из `clash_api` растут и на служебном
  трафике — ложные срабатывания дороже пользы, вернуться после 7a, если
  живых разрывов окажется мало).
