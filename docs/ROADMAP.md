## 0.6.16 — Фаза 6 (хвост) и раздельное туннелирование

Проверка кода 19.09.2026 показала конкретную причину, почему «не работает»
раздельное туннелирование по приложениям: экран выбора приложений строится
через `queryIntentActivities(ACTION_MAIN/CATEGORY_LAUNCHER)`, а в манифесте нет
`<queries>` и `QUERY_ALL_PACKAGES`. С Android 11 без этого система отдаёт
только «видимые» пакеты, и список почти пуст. Само правило в `establishTun`
(`addAllowedApplication`/`addDisallowedApplication`) написано верно. Что делаем:

- **Split по приложениям:** добавить `<queries>` для launcher-intent, показывать
  число найденных приложений; проверить на устройстве (INCLUDE и EXCLUDE) по
  внешнему IP.
- **Split по IP/доменам:** на устройстве не проверялся ни разу. Проверка живым
  трафиком (IP/CIDR, домен, поддомены), правка того, что сломано, unit-тесты
  на конфиг и `sing-box check`. Для Xray-моста правила берутся тем же конфигом
  sing-box.
- **6c-остаток:** `route.default_domain_resolver` (предупреждение sing-box,
  в 1.14 станет ошибкой) — с живой проверкой резолва домена прокси-сервера.
- **6e:** локализация (вынос строк в `strings.xml`, ru + en), Material You
  (dynamic color, Android 12+), AMOLED-чёрная тема, дополнительные иконки
  лаунчера.
- **6f:** хотспот-прокси: локальный SOCKS5/HTTP-листенер на `0.0.0.0` с
  логином/паролем, чтобы раздать VPN другим устройствам сети.

## 0.6.21 — подписки

- Клиент отдаёт свой **HWID** (стабильный идентификатор устройства в заголовке
  запроса подписки) — формат заголовка сверить с документацией панели до
  реализации.
- Вкладка «Серверы»: подписка показывается **с названием, которое отдал
  сервер** (заголовок `profile-title`), а не с тем, что ввёл пользователь.
- Все серверы подписки — в одном блоке: пинг отдельного сервера, пинг всей
  подписки, обновление подписки; блок сворачивается («спойлер»).
- Отдельные (не из подписки) серверы — отдельными строками: обновление, пинг.
- Автообновление подписок (WorkManager, интервал в настройках) и ручное.
  Обновление доступно у всех подписок.
- Синхронизация при обновлении: серверы, которые пропали из подписки, молча
  удаляются; новые — добавляются; ручное удаление сервера остаётся везде.
  Совпадение серверов определять по устойчивому ключу (адрес+порт+учётные
  данные), а не по названию.
- Обновление подписки уже атомарно (0.6.15) — не ломать.

## 0.7.0 — интеграция с проектом Hydra VPN

**Уточнено владельцем 19.09.2026:** панели свои (пока, возможно, не одна). Интеграция
идёт через Telegram-бота **Radar**: во вкладке «Профиль» — вход через TG в бот
Radar (когда в нём появится эта функция); через бота пользователь получает
подписки и оплачивает их, а владелец управляет панелями. Клиент к панелям
напрямую с учётными записями не ходит — только через Radar. Детали API бота
пока неизвестны, поэтому 0.7.0 начинается с согласования контракта с Radar.

Что это даёт клиенту:

- вход по аккаунту/токену; выдача подписки и конфигов бэкендом;
- HWID из 0.6.21 привязывает устройство к аккаунту и лимиту устройств;
- статус аккаунта (срок, трафик) на главном экране;
- приватный DNS проекта (`dns.hydravpn.us`) — как готовый пресет;
- единый слой «аккаунт + подписка» (KMP, см. `docs/MULTIPLATFORM.md`),
  общий для всех будущих клиентов.

Интеграцию ставим до desktop/iOS-клиентов, чтобы они сразу строились на ней.

## Фазы 9–12 — клиенты для других платформ

Стратегия — `docs/MULTIPLATFORM.md`: Kotlin Multiplatform только для
`data`-слоя (модели, парсеры, билдеры конфигов, слой аккаунта/подписок),
VPN-core и tun — отдельно на каждой платформе. Общее для всех: sing-box как
основное ядро, тот же формат подписок и HWID, интеграция из 0.7.0.

- **Фаза 9 — Windows.** Compose Multiplatform Desktop; tun через WinTun
  (sing-box с `auto_route`), права администратора или служба, автозапуск, трей,
  системный прокси как второй режим; установщик MSI/MSIX. Kill Switch — через
  Windows Filtering Platform.
- **Фаза 10 — Linux.** Тот же Desktop-UI; tun через `/dev/net/tun`
  (CAP_NET_ADMIN, systemd-служба или polkit), nftables для Kill Switch,
  пакеты AppImage/deb/rpm/Flatpak.
- **Фаза 11 — macOS.** Desktop-UI или нативный SwiftUI (решить после
  Windows); tun через `NEPacketTunnelProvider` (System Extension) — нужна
  подпись и нотаризация, Apple Developer Program.
- **Фаза 12 — iOS.** SwiftUI + Network Extension (`NEPacketTunnelProvider`),
  sing-box как `Libbox.xcframework`; жёсткий лимит памяти расширения ограничивает
  набор функций; App Store — отдельный риск по правилам для VPN.
- Позже (не планируем сейчас): ChromeOS, роутерные сборки.

## Дорожная карта UI/фич (согласована с пользователем, не в TODO ниже)

Живое тестирование на реальных устройствах регулярно обнаруживало критические
баги (см. «Честные оговорки») — поэтому, помимо инженерных TODO ниже, идёт
отдельный трек UI/UX-доработок по референсу стороннего клиента (показан
пользователем как пример хорошей организации экранов, не как код):

- ✅ **Фаза 0** (0.5.4-0.5.5): live-переключение сервера, утечка core/tun/fd,
  ANSI-мусор в логах, split tunneling верифицирован.
- ✅ **Фаза 1** (0.5.5): Настройки — хаб с подэкранами (Туннель/Split/Логи/
  О приложении), нижняя навигация свёрнута до 3 вкладок.
- ✅ **Фаза 1.5** (редизайн по артбуку «Hydra VPN Design Artbook», не
  версионирован отдельно): новая палитра Hydra Emerald (Abyss/Cyber Slate/
  #00E599) + вторая тема Monochrome Stealth с переключателем в Настройках
  (`ThemeMode`, `ThemeRepository`, `LocalHydraPalette` в `ui/theme/`);
  нижняя навигация расширена до 4 вкладок с иконками (добавлена **Профиль**);
  reactor-кнопка подключения на Canvas (кибер-контур + радар-пульс,
  явное состояние ERROR); карточки серверов — флаг вынесен в чип, пинг
  раскрашен по порогам, протокол-чип вместо точки; новый экран Профиля
  (статистика, sparkline-графики трафика, ссылка на GitHub); упрощённая
  геометрическая иконка приложения. Артбук — AI-моки, использован как
  референс стиля, не скопирован пиксель-в-пиксель (карта мира намеренно
  заменена на стилизованный кибер-радар, не географическую карту).
- ✅ **Фаза 2**: маршрутизация по IP/доменам — второй, независимый от
  по-приложениям, режим split tunneling (`SplitTunnel.netMode`/`netRules`,
  `NetRuleType` — IP/CIDR, домен, поддомены, ключевое слово). UI — вторая
  вкладка в Split-туннелинге («По IP/доменам», те же режимы Весь трафик/
  Только выбранные/Кроме выбранных). Реализовано через `route.rules` в
  `SingBoxConfigBuilder` (правила пользователя приоритетнее служебных
  dns/private-ip; `INCLUDE` меняет `final` на `direct`). **Честная оговорка**:
  работает только при подключении через sing-box-протоколы (VLESS/VMess/
  Trojan/SS/Hysteria2/TUIC/WireGuard) — у `VpnService.Builder` нет доменной
  маршрутизации, а точечное исключение IP (`excludeRoute`) доступно только
  с API 33 при minSdk 26 проекта, поэтому для SSTP/L2TP/AmneziaWG правила
  не действуют (явно показано в UI). Проверено **на full-сборке с реальным
  sing-box** (Xiaomi 12T Pro): туннель поднимается с правилом в `route.rules`,
  ядро не отвергает конфиг — значит JSON соответствует схеме sing-box 1.12;
  добавление/удаление/персист правил проверены в UI.
  **Осознанно не расширено** (изучено, но не реализовано — см. TODO №10):
  паритет для AmneziaWG через AllowedIPs не сделан, т.к. `AmneziaWgCore.start()`
  сейчас `throw NotImplementedError` (движок не подключён, ждёт
  `amneziawg-go.aar` из TODO №1), а `HydraVpnService.establishTun()` уже
  ставит OS-уровневый `addRoute("0.0.0.0/0")` до старта движка — сужение
  AllowedIPs дало бы чёрную дыру для несовпадающего трафика вместо bypass;
  настоящий фикс потребовал бы переписать общий `establishTun()` под
  awareness о `netRules`, рискованно менять ради нерабочего движка. SOCKS5-мост
  SSTP/L2TP в sing-box (чтобы и там работали IP/домен-правила) тоже не сделан:
  `TunBridge`/`PppSession` не имеют понятия о TCP-соединениях (только
  `sendIpPacket` целыми IP-пакетами) — потребовался бы собственный userspace
  TCP/IP-стек уровня gVisor netstack, непропорционально дорого ради этой фичи.
- ✅ **Фаза 3**: измерение пинга — `PingMeasurer` (новый, `data/net/`) меряет
  время TCP-connect до `address:port` (ICMP недоступен без root), переиспользуя
  паттерн `Socket()` + `SocketGuard.protect()` уже отработанный в `SstpCore`;
  корректно работает и при активном VPN, и без него (`protect()` — no-op,
  если сервис не подключён). Триггеры в UI: клик по значению/тексту «измерить»
  на карточке сервера (`MainViewModel.measurePing`) и «Обновить пинг» вверху
  экрана для всего списка сразу (`measureAllPings`); `measuringIds`
  показывает «измерение…» на карточке пока идёт замер. Группировка по

- **Фаза 7. Устойчивость рантайма** — отдельный трек, заведён по итогам аудита
  кода 19.09.2026 (статическое чтение всего `app/src`, **на устройстве

  пользователя, а не по сложности починки).

  Общий диагноз: приложение хорошо обрабатывает **отказ в момент
  подключения** (Kill Switch, честные исключения, аккуратная возня с fd и
  гонками в `doConnect()`), и почти никак — **отказ после того, как
  соединение поднялось**. Поднятый туннель никем не наблюдается: ни ядро,
  ни транспорт, ни смена сети не могут изменить `VpnState.state`. Худший
  сценарий — «зомби-туннель»: PPP закрыт/ядро умерло/Wi-Fi сменился на
  LTE, в UI по-прежнему «Туннель зашифрован», трафик не идёт, Kill Switch
  не срабатывает (он живёт только внутри `doConnect()`), и пользователь
  не знает, защищён он или нет.

  **Найденное — критическое (тихая потеря связи):**
  1. **Смерть ядра не отслеживается.** Интерфейс `VpnCore`
     (`vpn/core/VpnCore.kt`) — это `start()`/`stop()` без канала «я умер»:
     у ядра нет способа сообщить наверх об аварии. Места, где сигнал уже
     есть и выбрасывается в лог: `SstpCore.kt:168` (`onDown` PPP —
     `onLog(...)` и всё), `L2tpCore.kt:48-50` (`onTunnelDown` от
     StopCCN/CDN — `onLog(...)` и `running = false`). У sing-box канала нет
     вовсе: `BoxService` может закрыться, `SingBoxCore.service` об этом не
     узнает.
  2. **Смена сети не обрабатывается.** `HydraVpnService` не регистрирует
     `NetworkCallback` и никогда не зовёт `setUnderlyingNetworks()` —
     система продолжает считать подложкой ту сеть, что была на момент
     `establish()`. Единственный монитор сети в проекте живёт внутри
     `HydraPlatformInterface.startDefaultInterfaceMonitor()`
     (`SingBoxCore.kt`) и обслуживает только sing-box; для SSTP/L2TP
     транспортный сокет при Wi-Fi→LTE просто умирает.
  3. **Переподключения нет ни в каком виде** — ни retry с бэкоффом при
     неудачной попытке, ни reconnect после разрыва. Любая ошибка =
     `ERROR` до ручного тапа пользователя.
  4. **PPP без таймеров.** `sendLcpConfigRequest()` (`PppSession.kt:89`)
     отправляется ровно один раз: потерянный ConfReq/ConfAck — это
     ожидание до общего таймаута в `SstpCore`, без единой повторной
     попытки (RFC 1661 требует Restart-таймер). Свой Echo-Request мы не
     шлём — только отвечаем на чужой (`PppSession.kt:136`), так что
     молча умерший peer не детектируется.

  **Найденное — утечки потоков и ресурсов:**
  5. `TunBridge.stop()` (`TunBridge.kt:94`) ставит только `running = false`:
     поток `tun-ppp-read` (`:51`) остаётся навсегда висеть в блокирующем
     `input.read()`, `FileInputStream`/`FileOutputStream` поверх tun
     никогда не закрываются, поток `tun-bridge-stats` (`:79`) досыпает
     свой `Thread.sleep(1000)` без interrupt. При переподключении/смене
     сервера потоки накапливаются, а старый читатель продолжает толкать
     пакеты в уже закрытую сессию.
  6. `downBytes`/`upBytes` (`TunBridge.kt:31`) — обычные `Long`: пишутся из
     потока-читателя tun и из колбэка транспорта, читаются из потока
     статистики. Гонка, рваные значения счётчиков.
  7. `SubscriptionFetcher` (`:13`) создаёт **свой** `OkHttpClient` (со
     своим пулом потоков и коннекций) на каждый экземпляр
     `ServerRepository` — а репозиторий конструируется заново в
     `MainViewModel`, `HydraVpnService.doConnect()`, QS-плитке и
     `BootReceiver`.
  8. `AppDatabase.get()` (`:21`) — double-checked locking **без второй
     проверки** под `synchronized`: при гонке двух потоков собираются два
     инстанса Room на один файл.

  **Найденное — крэши и ANR-риски:**
  9. `startForegroundService()` не обёрнут ни в `BootReceiver.kt:37`, ни в
     `HydraQsTileService.kt:76`; `startForeground()` в
     `HydraVpnService.onStartCommand()` — тоже голый. На Android 12+ это
     `ForegroundServiceStartNotAllowedException` → краш процесса в фоне,
     который пользователь увидит как «после перезагрузки VPN не поднялся».
  10. Нет `Thread.setDefaultUncaughtExceptionHandler`: исключение в любом
      из ручных `thread {}` (`sstp-reader`, `l2tp-reader`, `tun-ppp-read`)
      уносит процесс, не оставив ни строчки в `LogStore` — разбирать
      потом нечего.
  11. `VpnState.log()` (`VpnState.kt:43`) — неатомарный
      read-modify-write `_logs.value = (_logs.value + …).takeLast(500)`,
      причём зовётся с JNI-потоков sing-box на горячем пути: часть строк
      теряется, и каждая строка аллоцирует новый список на 500 элементов.
      `LogStore.append()` (`:29`) складывает задачи в **неограниченную**
      очередь однопоточного executor'а — всплеск логов ядра растит кучу.
  12. `measureAllPings()` (`MainViewModel.kt:336`) — по корутине на сервер
      без ограничения параллелизма: на подписке в сотни серверов это
      сотни одновременных TCP-connect и столько же записей в Room.

  **Найденное — целостность данных:**
  13. `refreshSubscription()` (`ServerRepository.kt:34`) делает
      `deleteBySubscription()` + `upsertAll()` **не в транзакции**: падение
      между ними (или успешный ответ с пустым телом) стирает серверы
      подписки. Плюс id пересоздаются, из-за чего `lastServerId` повисает
      на несуществующем сервере.
  14. Room `version = 1` + `fallbackToDestructiveMigration()` — риск уже
      записан в 6d выше, здесь он просто самый дешёвый к починке из
      оставшихся.

  **План починки (порядок = порядок ценности, каждая подфаза
  самодостаточна и проверяема отдельно):**

  - ✅ **7a. Наблюдаемость туннеля** (0.6.14, **на устройстве не проверено,
    native-флейвор даже не компилировался** — см. CHANGELOG): в `VpnCore`
    появился `setDeathListener` (дефолтная реализация — no-op, поэтому ядра
    без такого сигнала правок не потребовали), и в него заведено то, что
    раньше уходило только в лог: обрыв TLS-канала / CALL_ABORT / закрытие
    PPP в `SstpCore`, StopCCN-CDN / закрытие PPP в `L2tpCore`, смерть
    процесса `:xray` (`onServiceDisconnected`) в `XrayCore`.
    `HydraVpnService` принимает сигнал через `Attempt` — маркер попытки,
    отличающий смерть у живого туннеля от смерти внутри `start()` (её
    по-прежнему разбирает catch в `doConnect`) и от эха уже проигравшей
    попытки при переключении сервера. Kill Switch вынесен в
    `enterKillSwitch()` и теперь защищает оба случая, а не только неудачное
    подключение; уведомление различает «Ошибка подключения» и «Туннель
    разорван».
    **Открытый хвост 7a — sing-box.** Признака «ядро умерло» в libbox не
    нашлось, и основной движок фазой пока НЕ покрыт. Отклонены два
    кандидата: `CommandClientHandler.disconnected()` — это обрыв нашего же
    локального сокета к `CommandServer`, возможный и при живом ядре, а
    ложное срабатывание погасило бы рабочее соединение (теперь просто
    пишется в лог); `CommandServerHandler.postServiceClose()` — по
    устройству libbox это запрос клиента на остановку, а не уведомление о
    смерти. Нужный признак надо сверять с настоящим `libbox.aar`
    декомпиляцией — тем же способом, которым в 0.6.6 сверялся API Xray.
    Пока его нет, 7b для sing-box бессмысленна: переподключать нечего,
    если разрыв не виден.
    Критерий готовности (НЕ выполнен, нужен телефон): убитый на сервере
    туннель за ≤5 с меняет UI и уведомление, а не остаётся «зашифрованным».
  - **7b. Переподключение.** Поверх 7a: `reconnect()` с экспоненциальным
    бэкоффом (1/2/4/8/16 с, потолок ~1 мин, счётчик сбрасывается после
    минуты живого соединения), состояние `RECONNECTING` в
    `ConnectionState` (UI-строка + отдельный вид reactor-кнопки), лимит
    попыток и честный переход в `ERROR` после него. Kill Switch держит
    tun «чёрной дырой» **всё время** переподключения — это главный
    смысл фазы. Отдельный тумблер «Переподключаться автоматически» в
    Настройках → Безопасность, рядом с Kill Switch.
  - **7c. Сеть под туннелем.** `NetworkCallback` уже в самом
    `HydraVpnService` (с `NET_CAPABILITY_NOT_VPN`, как в
    `HydraPlatformInterface` — тот же урок про собственный tun в роли
    «дефолтной сети»), `setUnderlyingNetworks(arrayOf(network))` при
    каждой смене, и триггер reconnect из 7b при смене транспорта
    (Wi-Fi ⇄ LTE). Для sing-box существующий монитор в
    `HydraPlatformInterface` остаётся как есть — фаза не должна его
    дублировать, только дополнить уровнем сервиса.
  - **7d. Жизненный цикл потоков и ресурсов.** `TunBridge.stop()` —
    закрывать потоки ввода-вывода (закрытие fd разблокирует
    `input.read()`), `join(timeout)` на оба потока, `interrupt()` для
    статистики; счётчики → `AtomicLong`. `PppSession` — Restart-таймер
    для ConfReq (3 попытки по 3 с, как в RFC 1661) и собственный
    LCP Echo-Request раз в 30 с с детектом трёх пропущенных ответов
    (это же и есть недостающий keepalive для 7a). Один общий
    `OkHttpClient` на процесс; `AppDatabase.get()` — вторая проверка под
    `synchronized`.
  - ✅ **7e. Дешёвая страховка** (0.6.15, кроме ограничителя лога — только
    компиляция stub в CI, живьём не проверено): `runCatching` вокруг всех

    сервис вместо падения); глобальный `UncaughtExceptionHandler` пишет
    стек в `LogStore` и ждёт сброса на диск (`flushBlocking`) до передачи
    системному обработчику; `VpnState.log()` переведён на атомарный
    `update {}` и получил `LogThrottle` (40 строк/с, WARN/ERROR не режутся,
    проглоченные считаются — вынесен отдельным классом с внешними часами
    ради JVM-тестов, как `LogFiles` в 6d); очередь `LogStore` ограничена
    2048 задачами с `DiscardPolicy`; `measureAllPings()` — `Semaphore(8)`;

    а не «импортировано 0 серверов»); вторая проверка под `synchronized` в
