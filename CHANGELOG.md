# Changelog

## [0.6.17] — Фаза 7: упавший туннель сам поднимается, смена сети

Собрано, юнит-тесты проходят; **ни один сценарий разрыва на устройстве не
воспроизводился** (нет живого сервера под рукой) — см. «Честная оговорка».

### Добавлено
- **Переподключение с бэкоффом (7b).** Новое состояние `RECONNECTING`. Если
  поднятый туннель разорвался (закрылся PPP, упал `:xray`, sing-box закрыл
  сервис), сервис сам пробует подняться на том же сервере: паузы 2, 4, 8, 16,
  затем 30 с, до 10 попыток; при появлении сети ждать бэкофф не нужно.
  Тумблер «Переподключение после разрыва» (Настройки → Безопасность),
  включён по умолчанию. Явное «Отключить» и системный отзыв VPN
  переподключение не запускают.
- **Kill Switch на всё время переподключения.** Прежний tun-«чёрная дыра» не
  закрывается, пока не появится новый; при неудачной попытке новый tun
  остаётся «дырой». Раньше разрыв живого соединения Kill Switch не защищал.
- **Смена сети (7c).** Сервис следит за физическими сетями и вызывает
  `setUnderlyingNetworks()` — Android больше не держит подложкой сеть,
  которая была при `establish()`. В лог пишется «Сеть: Wi-Fi / мобильная сеть».
- **Смерть sing-box (7a-остаток).** `CommandServerHandler.postServiceClose()`
  теперь сообщает о смерти сервиса (и для Xray-моста); штатная остановка
  смертью не считается.
- **PPP (7d):** Restart-таймер (повтор ConfReq каждые 3 с, до 10 раз, для LCP и
  IPCP) и свой LCP Echo-Request при тишине 15 с — три без ответа = разрыв.

### Исправлено
- `no available network interface` в первые доли секунды (№9): текущая
  физическая сеть отдаётся sing-box сразу при старте монитора, не дожидаясь
  колбэка.
- `TunBridge.stop()` не будил поток `tun-ppp-read` (блокирующий `read()` на
  tun): теперь `poll` с таймаутом 500 мс, поток дожидается остановки. Счётчики
  трафика моста — атомарные (их писали два потока).

### Честная оговорка
- Что именно вызывает `postServiceClose()` в libbox, в исходниках не сверено
  (Go-бинарь): по названию — закрытие сервиса не по нашей команде. Если
  sing-box умирает молча, сигнала не будет — тогда нужен активный «пинг»
  туннеля, он не сделан.
- Реальный обрыв (выключить Wi-Fi, убить сервер) и Wi-Fi ↔ LTE на телефоне не
  проверялись; порядок «закрыть старый tun → новый» при Kill Switch опирается
  на документированное поведение `VpnService.Builder.establish()`.


## [0.6.16] — Фаза 6 (хвост): хотспот-прокси, темы, языки, split-туннелирование

Собрано и проверено на сборке/юнит-тестах/`sing-box check`; **на устройстве
эта версия не прогонялась** (см. «Честная оговорка»).

### Исправлено
- **Раздельное туннелирование по приложениям: список приложений был почти
  пуст.** В манифесте не было `<queries>`, а с Android 11 без него
  `queryIntentActivities()` возвращает только «видимые» пакеты — выбрать в
  списке почти нечего. Добавлен `<queries>` по launcher-интенту (без
  `QUERY_ALL_PACKAGES`). Правило в `establishTun` (`addAllowed/DisallowedApplication`)
  было написано верно и не менялось. На экране теперь видно число приложений.
- **Split-туннелирование «не применялось».** Настройки читались только при
  подъёме туннеля, и изменение при включённом VPN выглядело как «не
  работает». Теперь через 1,2 с после правки (дебаунс) VPN сам
  переподключается на текущем сервере.
- **`route.default_domain_resolver`** (предупреждение sing-box, в 1.14 —
  ошибка): задан как `local`. Домен самого прокси-сервера резолвится
  платформенным резолвером мимо туннеля — резолвить его через тот же прокси
  было бы замкнутым кругом. Все 13 тестовых конфигов проходят настоящий
  `sing-box check` 1.12.9 без предупреждений.

### Добавлено
- **Хотспот-прокси (6f).** Настройки → Хотспот-прокси: `mixed`-inbound
  sing-box (SOCKS5+HTTP) на `0.0.0.0:<порт>`, только с логином/паролем
  (пароль по умолчанию генерируется, короче 6 символов не принимается;
  порт 1024–65535). Идёт через те же правила маршрутизации, что и tun. Показаны
  локальные адреса устройства со строкой подключения. Работает с
  движками sing-box и Xray Core; для SSTP/L2TP/AmneziaWG недоступно.
- **Темы:** «AMOLED Black» (чисто чёрный фон) и «Material You» (цвета из
  обоев, Android 12+; на старых версиях пункт помечен недоступным).
- **Иконки лаунчера:** выбор из пяти вариантов — «Как у темы», «Изумруд»,
  «Багровая», «Океан», «Янтарь» (два новых activity-alias). Старый
  тумблер «менять ярлык вместе с темой» мигрирует в «Как у темы».
- **Локализация (6e):** интерфейс на русском и английском, выбор языка в
  Настройки → Язык (системный / русский / English). Тексты вынесены в
  `values/strings_ui.xml` (английский, по умолчанию) и `values-ru`.

### Известные ограничения
- Логи подключения остаются на русском — это диагностика, а не интерфейс.
  Сообщения об ошибках разбора резервной копии тоже пока русские.
- Названия протоколов и часть технических подписей не переводились.
- IP/доменное split-туннелирование на устройстве по-прежнему не
  проверялось живым трафиком: причина «не работало» найдена только для
  списка приложений (выше). Хотспот-прокси проверен только конфигом и
  `sing-box check`, не подключением с другого устройства.


## [0.6.15] — Фаза 7e: страховка от крэшей и тихих потерь данных

Мелкие независимые правки по итогам аудита устойчивости — каждая закрывает
свой способ потерять данные или уронить процесс.

### Исправлено
- **Подписка больше не может стереть серверы.** Обновление подписки делало
  «удалить всё по подписке» и «записать новое» двумя отдельными вызовами:
  падение между ними оставляло подписку пустой. Теперь это одна транзакция
  Room. Вдобавок пустой разбор (панель ответила 200 с пустым телом или
  сменила формат) больше не применяется — прежний список остаётся на месте,
  а в логе видно причину отказа. Раньше любая ошибка загрузки выглядела как
  «импортировано 0 серверов».
- **Падение в фоне больше не молчит.** Добавлен обработчик аварийного
  завершения: стек пишется в файл лога до смерти процесса. В приложении
  несколько ручных потоков (`sstp-reader`, `l2tp-reader`, `tun-ppp-read`),
  и раньше исключение в любом из них уносило процесс без следов — logcat к
  моменту жалобы пользователя давно прокручен.
- **Запрет системы на запуск сервиса не роняет приложение.** Старт
  foreground-сервиса при автозагрузке, из плитки быстрых настроек и в самом
  сервисе был без обработки: на Android 12+ система вправе отказать
  (`ForegroundServiceStartNotAllowedException`), и это было падение в фоне,
  которое выглядело как «после перезагрузки VPN просто не поднялся».
  Теперь — понятная строка в логе, а для плитки ещё и открытие приложения.
- **Строки лога больше не теряются.** `VpnState.log()` обновлял список
  неатомарно (`_logs.value = _logs.value + строка`), а зовут его с разных
  потоков, в том числе с JNI-потоков sing-box: при одновременных вызовах
  часть строк просто пропадала.
- **Всплеск лога ядра не раздувает память.** Добавлен ограничитель: не более
  40 строк в секунду, проглоченные считаются и отмечаются одной строкой
  («пропущено строк лога: N»). Предупреждения и ошибки не режутся никогда.
  Очередь записи на диск тоже стала ограниченной (2048 задач) — раньше она
  была неограниченной и при быстром логе росла в куче, пока диск догоняет.
- **«Обновить пинг» на большой подписке не подвешивает устройство**: не
  больше 8 одновременных замеров вместо «по корутине на каждый сервер»
  (на подписке в сотни серверов это были сотни одновременных TCP-connect).
- **Room больше не собирается дважды.** В `AppDatabase.get()` не хватало
  второй проверки внутри `synchronized`: два потока, одновременно увидевшие
  пустой кэш, создавали по своему инстансу на один файл базы.

### Честная оговорка
Проверено по-настоящему только то, что не зависит от Android: `LogThrottle`
и `LogStore` скомпилированы и прогнаны отдельно (компилятор Kotlin из
дистрибутива Gradle + JUnit, без Android SDK) — 9 тестов OK, 6 новых на
ограничитель и 3 существующих на модель логов. Остальное покрыто только
компиляцией stub-сборки в CI: Android SDK в окружении нет, устройства тоже.
То есть именно те сценарии, ради которых правки делались — отказ системы в
запуске сервиса, аварийное завершение потока, гонка за создание базы, —
живьём не воспроизводились. Остальные существующие тесты прогнать не
удалось: они тянут androidx (Room), а `dl.google.com` в окружении закрыт —
на машине разработчика это обычный `./gradlew :app:testStubDebugUnitTest`,
и его стоит прогнать перед релизом.


## [0.6.14] — Фаза 7a: разрыв туннеля больше не остаётся незамеченным

### Добавлено
- **Ядро может сообщить, что туннель развалился** (`VpnCore.setDeathListener`).
  Раньше такого канала не было вовсе: интерфейс ядра состоял из `start()` и
  `stop()`, и всё, что случалось с уже поднятым соединением, уходило только
  в лог. Сервер прислал CALL_ABORT, закрылся PPP, оборвался TLS-канал, система
  убила процесс `:xray` — приложение продолжало показывать «Туннель
  зашифрован» и нулевой трафик, а Kill Switch не срабатывал, потому что жил
  только внутри попытки подключения. Теперь разрыв переводит состояние в
  ERROR, а при включённом Kill Switch tun остаётся поднятым «чёрной дырой»,
  и трафик не уходит в открытую сеть мимо туннеля.
- Уведомление различает «Ошибка подключения» (не удалось подключиться) и
  **«Туннель разорван»** (соединение было и пропало) — раньше во втором
  случае оно просто продолжало показывать «Туннель зашифрован».
- Источники сигнала: **SSTP** — обрыв TLS-канала, CALL_ABORT/CALL_DISCONNECT
  от сервера, закрытие PPP; **L2TP** — StopCCN/CDN от сервера, закрытие PPP;
  **Xray** — смерть процесса `:xray` (`onServiceDisconnected`), после которой
  трафик через локальный socks5 не пойдёт, даже если sing-box-мост и tun
  формально живы.

### Изменено
- Kill Switch вынесен в отдельный `enterKillSwitch()` и переиспользуется в
  обоих случаях — неудачное подключение и разрыв живого туннеля. Поведение
  при неудачном подключении не изменилось.
- Поля состояния `HydraVpnService` (`tun`/`core`/`tunFd`/`killSwitchBlocking`)
  помечены `@Volatile`: к ним теперь обращается ещё и колбэк смерти, который
  приходит с потока ядра — ридера SSTP/L2TP, JNI-потока sing-box или
  binder-потока `:xray`.
- `CommandClientHandler.disconnected()` у sing-box больше не пустой: обрыв
  канала статистики пишется в лог (см. оговорку ниже — смертью ядра он
  **не** считается).

### Не покрыто этой версией (честно)
**Для sing-box признака «ядро умерло» в libbox не нашлось**, поэтому основной
движок 7a пока не покрывает. Кандидаты, которые рассматривались и отклонены:
`CommandClientHandler.disconnected()` — это обрыв нашего же локального сокета
к `CommandServer`, он возможен и при живом ядре, а ложное срабатывание
погасило бы рабочее соединение; `CommandServerHandler.postServiceClose()` —
по устройству libbox это запрос клиента на остановку, а не уведомление о
смерти. Правильный признак нужно сверять с настоящим `libbox.aar`
декомпиляцией, как делалось для API Xray в 0.6.6 — отдельной задачей.
Watchdog по «трафик не растёт» сознательно не делался: счётчики растут и на
служебном трафике, ложные срабатывания дороже пользы.

### Честная оговорка
Ничего из этого не проверено на устройстве и **не проверено компилятором**:
в окружении, где делалась правка, нет Android SDK (`dl.google.com` закрыт
сетевой политикой), а CI собирает только stub-флейвор — то есть новый
`VpnCore` и `HydraVpnService` компиляцией CI покрыты, а правки в
`SstpCore`/`L2tpCore`/`XrayCore`/`SingBoxRuntime` (флейвор `native`, нужен
`.aar`) — нет. Перед выпуском обязательно локально: `./gradlew
:app:assembleNativeDebug` и живой тест — поднять SSTP/L2TP или Xray, убить
соединение на стороне сервера и убедиться, что UI и уведомление меняются
за секунды, а при включённом Kill Switch трафик не идёт мимо туннеля.
Unit-тестов на это нет: логика живёт в `VpnService` и на JVM без Robolectric
не запускается.


## [0.6.13] — Фаза 6d: резервная копия, сброс настроек, логи на устройстве

### Добавлено
- **Резервная копия** (Настройки → Резервная копия): все серверы, подписки
  и настройки — в один JSON-файл через системный выбор файла; восстановление
  заменяет всё содержимым файла (с подтверждением; VPN должен быть
  отключён). Файл разбирается целиком ДО любых изменений — повреждённая или
  чужая копия ничего не ломает. ID серверов сохраняются, поэтому «последний
  сервер» для плитки и автозапуска остаётся тем же. В файле ключи серверов
  открытым текстом — об этом предупреждение на экране.
- **Сброс настроек** к значениям по умолчанию; серверы и подписки остаются.
- **Логи на устройстве**: по файлу в день, срок хранения 1/3/7 дней, лимит
  5 МБ в день. По умолчанию сохраняются **только предупреждения и ошибки**:
  строки sing-box уровня INFO содержат адрес каждого соединения, т.е.
  историю посещённых сайтов. Полный журнал — отдельная опция с явным
  предупреждением. На экране логов — фильтр по уровню (все/предупреждения/
  ошибки), «В файл» (сохранённые дни + текущая сессия), размер и удаление
  сохранённого. Цель — разбирать сбои задним числом, когда logcat уже
  прокрутился (как было с «Ошибка: null» в 0.6.9).

### Изменено
- Все пять DataStore-файлов настроек объявлены в одном месте
  (`data/repository/Stores.kt`) под прежними именами — данные не мигрируют,
  у обновившихся ничего не теряется. Физически в один файл не сливались
  сознательно: бэкапу и сбросу нужна единая точка доступа, а не миграция.

### Известный риск (не исправлен в этой версии)
`AppDatabase` объявлена с `fallbackToDestructiveMigration()`: при любом
будущем изменении схемы Room без написанной миграции все серверы и
подписки молча удалятся. Резервная копия от этого страхует; перед первым
изменением схемы нужно писать Migration.

### Честная оговорка
Экраны и файловые операции на устройстве не проверялись (телефон не был
подключён). Проверено: 31 unit-тест (новые — кодек копии: полный
круг с сохранением типов, значения по умолчанию, отказ на чужих/битых
файлах; уровни логов на реальных строках; ротация файлов),
`assembleNativeDebug`/`assembleStubDebug`.

## [0.6.12] — GeoIP-маршрутизация по любым странам

### Добавлено
- **Выбор стран для geo-маршрутизации** (Настройки → Маршрутизация):
  вместо одной РФ — любые из ~250 стран, можно несколько сразу (например,
  Россия + Беларусь + Казахстан напрямую). Поиск по названию или ISO-коду.
  Режимы переименованы в «Выбранные страны напрямую / через прокси».
- Все базы IP вшиты в APK (`assets/geoip/<cc>.srs`, ~3.8 МБ) — работают без
  интернета, без загрузок при подключении. Источник тот же:
  MetaCubeX/meta-rules-dat, ветка `sing`.
- **Доменные базы есть только у пяти стран** — Россия, Китай, Иран,
  Португалия, Туркменистан (`assets/geosite/`). У остальных маршрутизация
  только по IP, и это прямо показано в списке («IP» / «IP+домены»): сайт
  такой страны, размещённый на зарубежном CDN, по IP определится как «не её».

### Изменено
- Режимы `RU_DIRECT`/`RU_VIA_PROXY` → `DIRECT`/`VIA_PROXY`; сохранённые
  старые значения мигрируют автоматически, выбор стран по умолчанию — РФ,
  так что у обновившихся поведение не меняется.
- Старые `assets/geoip-ru.srs`/`geosite-ru.srs` заменены на
  `geoip/ru.srs`/`geosite/ru.srs` (доменная база РФ байт-в-байт та же,
  IP-база — свежее обновление источника).

### Честная оговорка
Не проверено на устройстве с живым трафиком. Проверено: 25 unit-тестов;
все 12 вариантов конфига приняты `sing-box check` 1.12.9; отдельно — конфиг
сразу со всеми 255 вшитыми базами принят `check` (который, как проверено,
действительно открывает и парсит файлы: на отсутствующий файл и на мусор
падает) и реально запускается `sing-box run` (0,4 с).

## [0.6.11] — Фаза 6c: TLS-фрагментация и MTU

### Добавлено
- **Фрагментация TLS-рукопожатия с прокси-сервером** (Настройки →
  Маршрутизация): «По TLS-записям» (`tls.record_fragment`, почти без потерь

  медленнее подключается). Против DPI, который ищет имя сайта (SNI) в одном
  пакете. Действует только в движке sing-box и только на VLESS/VMess/Trojan

  Core рукопожатие делает сам Xray. Выключено по умолчанию.
  Сознательно НЕ через `route-options.tls_fragment`: та опция режет
  рукопожатия проходящих через туннель соединений — их DPI не видит, он
  видит только соединение к прокси.
- **MTU туннеля**: «Авто (9000)» (прежнее значение) / 1500 / 1400 / 1280.
  Одно значение и для `VpnService.Builder`, и для tun-инбаунда sing-box —
  они должны совпадать. Для SSTP/L2TP действует не выше 1400.

## [0.6.7] — Xray Core: живой тест вскрыл и починил 5 багов

Живое тестирование на реальном устройстве (OnePlus CPH2747) сразу после
публикации 0.6.6 нашло пять отдельных багов подряд — Xray Core падал/не
подключался при каждой попытке. Все найдены и исправлены в этой версии;
VLESS через Xray Core теперь поднимается и передаёт трафик на реальном
устройстве.

### Исправлено
- **`UnsatisfiedLinkError` при старте `:xray` — грузилась не та `.so`.**
  Дедуп дублирующихся классов `go.*` (оставляли только копию от libbox)
  ломал `LibXray._init()` — `go.Seq.<clinit>` зашивает имя нативной
  библиотеки на этапе сборки (`"box"` vs `"gojni"`), копии не
  взаимозаменяемы. Попытка переименовать пакет (`go`→`xraygo`) тоже не
  сработала — у gomobile implicit JNI-linking, переименование класса рвёт
  связь с уже скомпилированными символами `.so`. Итоговое решение — классы
  Xray грузятся в процессе `:xray` изолированным `DexClassLoader` (свой
  `classes.dex`, собран из нетронутого `classes.jar` через `d8`), а не как
  обычная Gradle-зависимость.
- **`DexClassLoader` тоже находил не ту `.so` — через родителя.** Обычный
  `parent`-classloader делегирует поиск классов родителю первым, а родитель
  (classloader процесса `:xray`) всё равно видит `go.Seq` от libbox —
  тот же баг, но через классовую делегацию, а не merge дексов. Фикс:
  `parent = null` у `DexClassLoader` (только boot-classloader).
- **`Writable dex file ... is not allowed`.** ART отказывается грузить dex,
  пока файл ещё доступен на запись самому процессу (защита от подмены кода
  в рантайме) — `libxray.dex` теперь помечается read-only сразу после
  копирования из assets.
- **`fdsan`-краш (SIGABRT) в `HydraVpnService` при ошибке подключения.**
  Код отката всегда пытался закрыть и `ParcelFileDescriptor`, и raw fd
  через `adoptFd()` — безопасно, только если нативное ядро успело
  `detachFd()` СРАЗУ (как sing-box). `XrayCore` мог упасть раньше — тогда
  оба пути закрывали один и тот же номер fd, второй раз уже освобождённый
  (и потенциально переиспользованный) — `fdsan` валил процесс. Теперь
  ровно один путь, по факту владения (`ParcelFileDescriptor.valid()`).
- **`geoip:private` без файла `geoip.dat`.** `XrayConfigBuilder` ссылался
  на встроенную базу GeoIP для проверки приватных IP — файла в
  embedded-сборке нет, Xray падал на старте конфига. Заменено на явные
  CIDR-диапазоны (RFC 1918 + loopback/link-local), без внешних файлов.

## [0.5.3] — краш на каждом запуске + «подключено, но нет интернета»
Оба бага найдены и исправлены живой отладкой на реальном устройстве
(OnePlus 15, Android 16, через adb: logcat, dumpsys dropbox/connectivity,
live-переустановка) — 0.5.2 не переживал запуск на реальном железе.

### Исправлено
- **Краш на КАЖДОМ запуске приложения**: `object VpnState` инициализировал
  поле `_logs` раньше `fmt` (используется внутри `line()`) — на момент
  вычисления `_logs` поле `fmt` было ещё `null`, `fmt.format(Date())` падал
  с `NullPointerException` в `<clinit>`. `VpnState` впервые трогается в
  конструкторе `MainViewModel`, создаваемой в `MainActivity.onCreate()` до
  отрисовки UI, — падало на каждом запуске, в любом флейворе, независимо от
  версии Android. Похоже, это и был исходный краш из самой первой жалобы.
- **Второй JNI-краш**: `startDefaultInterfaceMonitor` регистрировал
  `ConnectivityManager.NetworkCallback` на внутреннем потоке
  `ConnectivityManager` — вызов `listener.updateDefaultInterface()` (JNI в
  Go) с этого «чужого» потока воспроизводимо валил процесс нативным
  `SIGABRT` (тумбстоун, поток `ConnectivityThread`), что не перехватывается
  никаким `try/catch`/`runCatching` на стороне Kotlin. Теперь колбэк
  регистрируется на выделенном `HandlerThread`.
- **«Подключено», но нет интернета** (0.0 MB, 100% исходящих TCP-соединений
  sing-box падали с `no available network interface`):
  - `registerDefaultNetworkCallback()` у **владельца** VPN воспроизводимо
    репортил **собственный `tun0`** как «дефолтную сеть» вместо реального
    Wi-Fi/мобильного интерфейса — sing-box пытался биндить исходящий сокет
    на собственный туннель. Заменено на `registerNetworkCallback()` с явным
    `NetworkRequest`, требующим `NET_CAPABILITY_NOT_VPN`.
  - `getInterfaces()` никогда не заполнял поле `flags` (Go `net.Flags`) —
    все интерфейсы выглядели «не поднятыми» (flags=0), sing-box отбрасывал
    их все как непригодные.
  - `getInterfaces()` отдавал голый `hostAddress` без CIDR-маски, а для
    IPv6 link-local адресов ещё и с zone-id (`fe80::...%rmnet_data0`) —
    Go-паника `netip.ParsePrefix`.
  - Добавлен `VpnService.protect(fd)` через `SocketGuard` как официальный
    резервный механизм (`usePlatformAutoDetectInterfaceControl = true`).
- Экран «Настройки» показывал захардкоженную версию (`Hydra 0.5.1`,
  отставшую от реального релиза) — теперь берётся из `BuildConfig.VERSION_NAME`.

### Изменено
- `VpnState.log()` дублирует сообщения в logcat (тег `HydraCore`) — упрощает
  диагностику на реальном устройстве без пересборки debug-APK ради
  временных логов.
- `buildFeatures.buildConfig = true` — включено для доступа к
  `BuildConfig.VERSION_NAME` из UI.

### Верификация
- Подтверждено на реальном устройстве: чистая установка → запуск без
  краша → подключение → загрузка настоящих страниц в браузере
  (accessibility-дамп подтвердил результаты поиска с внешним IP через
  VPN-сервер, отличным от реального IP телефона).
- `no available network interface` сведено со 100% исходящих TCP-соединений
  до единичных в первую долю секунды при старте (до первого сетевого
  колбэка) — не устранено полностью, но не мешает работе.

## [0.5.2] — критические фиксы краша + верификация native-сборки
### Исправлено
- **Краш при каждом подключении VPN на Android 14+**: `AndroidManifest.xml`
  объявлял `HydraVpnService` с `android:foregroundServiceType="systemExempted"`,
  а разрешение `FOREGROUND_SERVICE_SYSTEM_EXEMPTED` имеет уровень защиты
  `signature|privileged` и никогда не выдаётся сторонним приложениям —
  `startForeground()` в `HydraVpnService.onStartCommand` падал с
  `SecurityException` при каждой попытке подключения. Заменено на
  `specialUse` + `<property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE" android:value="vpn" />`.
- **Краш userspace-PPP (SSTP/L2TP) на битых TCP-пакетах**:
  `TunBridge.fixChecksums` не проверял границы буфера для TCP-ветки (в
  отличие от UDP-ветки рядом) — фрагментированный/укороченный TCP-пакет от
  сервера приводил к `ArrayIndexOutOfBoundsException` в фоновом потоке без
  обработчика и убивал процесс целиком. Добавлена проверка `p.size >= ihl + 18`.
- **ANR на экране Split Tunneling**: `PackageManager.queryIntentActivities()`
  вызывался синхронно на главном потоке при первом рендере списка
  приложений — перенесено на `Dispatchers.Default` через `LaunchedEffect`.

### Добавлено
- Runtime-запрос `POST_NOTIFICATIONS` (Android 13+) в `MainActivity.onCreate` —
  разрешение было объявлено в манифесте, но никогда не запрашивалось, из-за
  чего постоянное уведомление о статусе VPN не показывалось пользователю.

### Изменено (накоплено после 0.5.1, ранее не отражено в Changelog)

## [0.3.0] — SSTP, L2TP и userspace-PPP-стек
### Добавлено
- **Userspace PPP-стек на Kotlin** (`vpn/ppp`, без нативных .aar):
  - `Md4` (RFC 1320 — нужен для MS-CHAPv2, в JCE отсутствует);
  - `MsChapV2` (RFC 2759 + RFC 3079 GetMasterKey — CMK для SSTP crypto-binding),
    константы и тест-векторы сверены с RFC;
  - `Ppp` — фрейм-кодек (LCP/IPCP/CHAP/PAP, опции);
  - `PppSession` — машина состояний: LCP → MS-CHAPv2/PAP → IPCP (IP/DNS по IPCP);
  - `TunBridge` — мост tun ⇄ PPP: SNAT 172.19.0.1 ⇄ назначенный IP,
    инкрементальная коррекция чек-сумм IPv4/TCP/UDP (RFC 1624).
- **SSTP** (`SstpCore`, MS-SSTP): TCP → TLS 1.2/1.3 (SNI, опция allow_insecure),
  HTTP SSTP_DUPLEX_POST /sra_{BA195780-…}/, CALL_CONNECT_REQUEST/ACK,
  PPP поверх SSTP-кадров, CALL_CONNECTED с crypto-binding
  (Compound MAC = HMAC-SHA1/SHA256 от CMK), ECHO-поддержка, проверка хэша
  сертификата сервера из ENC_INFO.
- **L2TP** (`L2tpCore` + `L2tpTransport`, RFC 2661): SCCRQ→SCCRP→SCCCN,
  ICRQ→ICRP→ICCN (AVP по RFC §4.4), Ns/Nr + ZLB-ack, ретрансмиссия,
  опциональный tunnel-auth (Challenge/Challenge Response, MD5),
  PPP поверх UDP-канала данных. Без IPsec/ESP (недоступен в userspace).
- **PPTP** (`PptpCore`): честный отказ — GRE (IP-протокол 47) требует
  raw-сокетов/root, стек удалён из Android 12/13.
- `SocketGuard` — protect() сокетов userspace-ядер против петли маршрутизации.
- Парсинг ссылок `sstp://`, `l2tp://`, `pptp://` (user:pass@host:port).

### Изменено
- Ветка IKEv2/IPsec (`Ikev2Connector`) удалена: L2TP теперь настоящий
  userspace-PPP; `Engine.IKEV2` → `Engine.USERSPACE`/`Engine.UNAVAILABLE`.
- MTU tun для PPP-движков — 1400 (иначе фрагментация на TLS/UDP).

### Известные ограничения
- SSTP/L2TP требуют проверки на устройстве против реального SoftEther/Mikrotik
  (согласование PPP, crypto-binding, SNAT в `TunBridge`).
- L2TP без IPsec: шифрование только на уровне PPP (MS-CHAPv2 не шифрует данные);
  для защищённого канала используйте SSTP/WireGuard.
